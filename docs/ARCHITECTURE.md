# Architecture

How the frontend is put together, and why each piece sits where it does.

---

## 1. Layering

Data flows in one direction. Each layer only knows about the one beneath it.

```
routes/                     screens; own local UI state and compose everything below
  └── global_components/    reusable presentation, no data fetching of its own
        └── hooks/          useSession, useTheme — derived, app-wide state
              └── services/ queries + mutations (TanStack Query) over api.ts
                    └── utils/types + lib/  contracts and pure helpers
```

Two rules keep this honest:

- **Components never call `fetch` or `requests` directly.** They call a hook from
  `services/queries` or `services/mutations`. That keeps every cache key, retry
  policy and toast in one place.
- **`utils/` and `lib/` never import from `components/` or `routes/`.** They are
  leaves — pure types and pure functions.

---

## 2. The API client

`src/services/api.ts` exports a single `requests<T>()` helper over `fetch`.

It owns four responsibilities:

1. **URL assembly.** `${VITE_APP_BASE_URL}api/v1/${path}` plus a query string
   built from the `query` option. Values that are `undefined`, `null`, `""` or
   the literal `"ALL"` are dropped, so a UI filter set to "All statuses" simply
   omits the parameter rather than sending a bogus one.
2. **Auth.** Reads the JWT from the cookie unless a caller passes an explicit
   `token`, or opts out with `authenticated: false` (login and register).
3. **Envelope unwrapping.** The API answers uniformly with
   `{ success, message, data, count? }`. A response that is not `ok`, or whose
   `success` is `false`, is thrown as an `APIError` carrying `status` and any
   per-field `errors` from the Zod validation middleware.
4. **401 handling.** Clears the cookie and raises a toast. The query layer then
   sees an unauthenticated session and the route guard redirects.

`checkHealth()` hits `/health`, which sits outside the `/api/v1` prefix.

## 3. Server state

TanStack Query owns everything that comes from the API. There is no Redux, no
Zustand and no global data context.

**Query keys** live in `src/services/queryKeys.ts`. Mutations invalidate by
prefix, so `queryKeys.rooms.all` clears every room list regardless of the
filters baked into its key.

**`select` unwraps in the hook.** Query hooks return the useful payload, not the
envelope:

```ts
useQuery({
  queryFn: () => requests<RoomListResponse>("rooms", { query }),
  select: (response) => response.data.rooms,
});
```

So a route writes `const { data: rooms = [] } = useGetRooms()`, never
`response.data.data.rooms`.

**Defaults** (in `main.tsx`): `staleTime` 30s, no refetch on window focus, and a
retry policy that gives up immediately on 401 and 403 — a wrong token or a wrong
role does not improve on retry.

**Invalidation.** Every reservation transition also moves room availability and
shifts the report numbers, so `useReservationInvalidation()` refreshes
reservations, rooms and reports together. Room mutations refresh rooms and
reports.

## 4. Authentication and session

There is no auth context provider. The session *is* a query.

```
useLogin()  ──▶ POST /auth/login
                 ├─ setToken(jwt)                     cookie, 7-day expiry
                 └─ queryClient.setQueryData(session) primes the cache

useSession() ──▶ useGetSession() ──▶ GET /auth/me
                 enabled only when a token cookie exists
```

`useSession()` (`src/hooks/useSession.ts`) is the single place the UI asks *who
is signed in and what may they do*. It derives `isAdmin`, `isStaff`,
`bookableCategory` and `hasRole()` from the user's role, so authorisation rules
are stated once rather than re-derived in each screen.

**Token storage.** A cookie (`stayhub_token`), not `localStorage`, matching the
convention in the sibling projects. It is `sameSite: lax` and gains `secure`
automatically when served over HTTPS. Because the API issues stateless JWTs with
no revocation endpoint, signing out is purely client-side: drop the cookie and
call `queryClient.clear()`.

**Route guards.** `ProtectedRoute` wraps the dashboard layout and, where needed,
individual screens with a `roles` list. It captures the redirect target once on
mount and fires at most one navigation — reading the location live caused a
`/login?redirect=/login?redirect=…` loop. The `redirect` search parameter is
sanitised on the way back in: same-origin relative paths only, never `/login`.

The guard is a convenience, not a security boundary. The API re-checks the token
and the role on every request.

## 5. Routing

File-based, generated by `@tanstack/router-plugin` into `src/routeTree.gen.ts`
on dev start and build. Never edit that file.

```
routes/
├── __root.tsx              outlet only; each shell owns its own chrome
├── index.tsx               /            public landing
├── login.tsx               /login       validateSearch → { redirect? }
├── register.tsx            /register
└── dashboard/
    ├── route.tsx           /dashboard   ProtectedRoute + DashboardShell
    ├── index.tsx           /dashboard
    ├── rooms/index.tsx     /dashboard/rooms
    ├── reservations/       /dashboard/reservations   GUEST, STUDENT
    ├── front-desk/         /dashboard/front-desk     RECEPTIONIST, ADMIN
    ├── manage-rooms/       /dashboard/manage-rooms   ADMIN
    └── reports/            /dashboard/reports        ADMIN
```

`dashboard/route.tsx` is a **layout route**: it renders the auth gate and the
sidebar chrome once, and every child renders into its `<Outlet />`.

Files and folders prefixed with `-` are ignored by the route generator, which is
what makes `local_components/<Name>/-index.tsx` co-location work.

`autoCodeSplitting` is on, so each route ships as its own chunk. Recharts lands
only in the reports chunk.

## 6. Forms

React Hook Form with Zod resolvers. Schemas live in
`src/global_components/-formSchemas.ts` and mirror both the API's own Zod
schemas *and* the rules its controllers enforce imperatively — the
category/room-type pairing, the student-ID requirement, date ordering. Catching
those client-side turns a 400 round trip into inline field feedback.

Because `z.coerce.number()` widens the *input* type to `unknown` (a number input
hands back a string), forms that coerce are typed on both shapes:

```ts
useForm<RoomSchemaInput, unknown, RoomSchemaType>({ resolver: zodResolver(roomSchema) })
```

`handleSubmit` then receives the parsed output type.

---

## 7. The noon checkout cycle

The API computes stay length as `Math.ceil((checkOut - checkIn) / 1 day)`, with
a floor of one night, against a 12:00 PM cutoff.

`src/lib/date.ts` mirrors that exactly. `toCutoffISOString()` snaps a
`<input type="date">` value to noon before sending it, so whole-day differences
land on exact multiples of 24 hours and the nightly total previewed in the
reserve dialog is the one the server persists.

---

## 8. Theming

Tokens are defined once in `src/index.css` as CSS custom properties on `:root`
and `.dark`, then bridged into Tailwind via `@theme inline`. Components only
ever reference semantic utilities (`bg-card`, `text-muted-foreground`), never
raw colours — which is what let the whole palette be swapped to monochrome by
editing one file.

`useTheme()` is a dependency-free `useSyncExternalStore` over `localStorage`
plus a `prefers-color-scheme` listener. `initializeTheme()` runs in `main.tsx`
before React mounts, so the first paint is already correct and there is no
flash.

See [UI_GUIDE.md](UI_GUIDE.md) for the palette itself.
